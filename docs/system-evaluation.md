# dsh-effort-slider 系统全面评估报告

- 评估日期：2026-10-01
- 评估对象：v0.4.0（DSH 0.2.0-rc.2 适配版），commit d822862 + 工作区未提交改动（npm 包名改名文档同步）
- 评估基线验证：`pnpm test` 四层测试全部通过（host 单测 / host-apply / host-integration / client smoke），`pnpm typecheck` 无错误。以下所有问题都是在「测试全绿」的前提下仍然存在的缺陷，说明它们落在现有测试的盲区里。
- 评估材料：`src/index.ts`、`src/effort-core.ts`、`src/client/`（index / EffortPanel / useWebglFire / shaders / directory / effortColors / CSS）、`tsdown.config.ts`、`cordis.patch.yml`、`test/` 全部四层、README 及多语言翻译。

## 0. 评估范围与维度映射

本系统是一个 DSH（DeepSeek Harness）插件，由两个半区组成：

| 半区 | 代码 | 职责 |
| --- | --- | --- |
| 浏览器半区（前端界面） | `src/client/` → `lib/client.js` | 拦截模型菜单「推理等级」行，弹出 Effort 滑杆面板（React + WebGL 火焰），读写会话共享模型目录 |
| 宿主半区（后端服务） | `src/index.ts` + `src/effort-core.ts` → `lib/index.js` | 通过 SettingsForms 接缝为缺少推理元数据的自定义模型热补写 `reasoningEfforts` / `compat` 线方言配置 |

评估要求里的部分维度在本系统中没有直接对应业务，按最贴近的对应物映射：

| 要求的维度 | 本系统中的对应物 |
| --- | --- |
| 预约流程的便捷性 | 「调档交互流程」：打开菜单 → 拖动 → 松手吸附 → 持久化（系统无预约业务，此项按交互主流程评估） |
| 数据处理与存储效率 | pi-ai 条目配置的读（describe）/写（mutate，含 models 整数组替换）路径、内存缓存 |
| 权限管理机制 | 服务注入面（`inject: ['llm','settings']` / `['sessions','modelDirectories']`）、bundle patch、凭据边界 |
| 系统响应速度 | 拖动写入节流、MutationObserver 扫描、WebGL 渲染循环、供给重试时序 |

## 1. 总体健康度（分维度评分，满分 5）

| 维度 | 评分 | 结论 |
| --- | --- | --- |
| 安全性 | 5 | 无凭据读取、无自有网络请求、React 转义渲染无注入面、宿主写入仅限 reasoningEfforts/compat 两个字段。当前未发现安全问题 |
| 功能完整性 | 4.5 | 核心功能（滑杆调档 + 通用供给）完整且幂等；缺的是「配置错了方言」时的诊断能力 |
| 用户体验 / 交互流程 | 4 | 主流程（点击→拖动→吸附→着色）顺畅，拖动防抢滑块的处理很细致；扣分在错误提示误导、面板定位不跟随滚动 |
| 可维护性 | 4 | 纯逻辑抽离（effort-core）、四层测试、disposer 生命周期管理是亮点；无 CI、常量双份、部分死代码 |
| 扩展性 | 4 | 方言表是干净的查表扩展点；但菜单行识别文本、UI 文案不可扩展 |
| 性能效率 | 3.5 | WebGL 循环管理得当（idle 计数、context lost 恢复）；全文档 MutationObserver 常开是持续小开销 |
| 兼容性 | 3 | 强绑定 DSH 0.2.0-rc.2（社区插件常态，可接受）；但菜单行识别只认中英两种文案，其余语言静默失效 |

**一句话总结**：这个插件的安全边界和工程分层做得好于绝大多数同类社区插件；真正的短板集中在「异常路径的用户反馈」——正常路径层层测试保护，异常路径（目录加载失败、写入失败、供给静默失效、非中文英文界面）几乎全部静默。

## 2. 建议清单（按优先级）

> 优先级定义：**P0** = 已经在误导用户或丢失反馈，应立即修；**P1** = 特定但现实条件下功能静默失效或丢数据；**P2** = 体验/性能/工程质量债，值得排期；**P3** = 新功能提案与代码卫生。实施难度：低 ≈ 半天内，中 ≈ 1–2 天，高 ≈ 需要设计权衡或依赖宿主能力。

### P0-1 面板把「加载中 / 加载失败 / 不支持」三种状态合并成一条错误提示

- **位置**：`src/client/effort/EffortPanel.tsx:244-248`（overlay 判定）、`EffortPanel.tsx:53-55`（load 失败只 console.warn）、`src/client/effort/directory.ts:52-55`（`status`/`error` 字段定义了但面板从未消费）
- **问题描述**：overlay 只区分 `state === null`（显示「模型目录加载中…」）和其余情况（显示「当前模型不支持思考强度调节」）。目录快照存在但还在加载时（`status: 'loading'`、`groups` 为空），以及加载失败时（`status: 'error'`），都会落到「当前模型不支持思考强度调节」这条文案上。
- **优化建议**：按 `state.status` 三分支渲染：`loading` → 「模型目录加载中…」；`error` → 展示 `state.error` 原文（或统一文案）+「重试」按钮（重新调用 `directory.load()`）；`ready` 且确无 efforts → 才显示「当前模型不支持思考强度调节」。同时在 smoke 测试补一个 `status: 'error'` 目录的用例。
- **实施难度**：低。纯前端分支 + 一个测试用例，不动任何写入路径。
- **为什么这么定级**：这不是功能缺失，而是唯一的错误提示面在「说谎」——三种完全不同的故障被翻译成同一条会把用户引向错误排障方向的话。面板刚打开、目录尚未就绪的瞬间就会闪现这条错误信息，所以触发条件并不罕见；而它又是 P0 里唯一修复成本极低的一项。
- **一句话版本**：面板在目录还在加载或加载失败时，会告诉用户「你的模型不支持思考强度」，把环境故障伪装成模型能力问题。
- **一个需要知道的取舍**：`error` 文案来自目录服务，语言和措辞不受本插件控制，直接展示可能与面板其他中文文案混杂；折中做法是默认展示统一中文文案、`console.warn` 带出原始 error，而不是把原始文案直接推给用户。
- **事故是怎么发生的**：用户网络抖动或 DSH 宿主目录装配失败 → 打开面板看到「当前模型不支持思考强度调节」→ 用户以为自己配的第三方模型有问题，去查模型配置、甚至提 issue 说插件坏了 → 实际重启 DSH 就好。维护者收到一个无法复现的 issue（自己环境里一切正常）。

### P1-1 拖动写入失败完全静默，用户以为调成了实际没调成

- **位置**：`src/client/effort/EffortPanel.tsx:149-155`（`directory.select(...).catch(console.warn)`）
- **问题描述**：`select` 失败只有 DevTools 里一条 warn，面板 UI 无任何反馈；目录状态里的 `error` 字段同样未被消费。README 说「官方入口自己保留错误提示面」，但面板是独立浮层，官方提示可能在面板打开期间不可见。
- **优化建议**：`select` 失败时把面板 header 的档位状态文字临时切换为错误态（如红色「写入失败」并保留 2 秒），同时不回退滑块位置（用户可直接重拖）；可选做一次自动重试。
- **实施难度**：低-中。需要在面板里新增一个短暂的错误 UI 状态，并处理与拖动状态的叠加。
- **为什么这么定级**：这是「数据丢失且无感知」类缺陷——用户明确执行了一个操作，系统没执行成功却表现为成功。发生频率不高（依赖目录服务暂时性拒绝），但后果是用户对档位的认知与实际不符，且无法从界面察觉。
- **一句话版本**：拖动松手后写入若被拒绝，面板毫发无损地显示成功，实际档位还停在旧值。
- **一个需要知道的取舍**：面板内加错误提示会让 UI 状态机复杂化（拖动中失败、松手后失败、重试中再失败）；最简方案是只做「状态文字变红 + 不动滑块」，把重试策略留给用户重拖一次。
- **事故是怎么发生的**：API 网关限流或会话目录短暂只读 → 用户把档位拖到 max、看到面板显示 Ultracode → 放心地跑了一个昂贵任务 → 事后发现请求一直是按 low 发出的（旧档位），账单和预期对不上。

### P1-2 菜单行识别只认中英文案，其他语言/措辞变动下插件静默失效

- **位置**：`src/client/index.ts:37`（`EFFORT_LABEL_TEXTS` 只有 `推理等级`/`Effort`）、`client/index.ts:75, 201`（`text.startsWith(...)`）、`client/index.ts:97-99`（触发按钮 aria-label 同样只认两种语言）
- **问题描述**：整条拦截链（识别 Effort 行 → 拦截点击 → 着色）全部依赖菜单行文本前缀匹配。DSH 未来增加其他界面语言，或官方改动措辞（如「推理等级」改为「推理强度」）时，点击不再被拦截、着色不再生效，且没有任何警告。
- **优化建议**：三步走：① 识别失败时在面板初始化后输出一次性 `console.warn`（有诊断线索）；② 识别逻辑改为「文本 + 结构」双通道（`row.closest('[role="menu"]')` 内的 menuitem 且含 chevron svg 等），文本命中只是加分项；③ 把文案集合提取成可扩展常量，后续加语言零成本。
- **实施难度**：中。结构特征需要对照官方真实 DOM 反复验证，是纯人工核对的活。
- **为什么这么定级**：失效模式是最恶劣的一种——完全静默。用户装了插件、看不到任何报错，功能却整个不存在。README 有七种语言翻译说明用户群是多语言的，这个风险不是假设。
- **一句话版本**：只要官方菜单的措辞或语言不在预设的两个词里，插件就无声消失，连一条日志都没有。
- **一个需要知道的取舍**：纯结构匹配（不看文本）会更早失效于官方结构调整，纯文本匹配则失效于措辞变化；双通道并集最稳，但每加一条规则就多一分误拦截其他菜单行的风险（例如设置页里恰好也有以「Effort」开头的按钮），所以建议同时加 `role="menu"` 容器限定。
- **事故是怎么发生的**：DSH 某个版本把菜单文案从「推理等级」改成「推理强度」（或新增日语界面）→ 一夜之间所有用户的插件失效 → issue 区出现「plugin doesn't work」，维护者自己是中文界面无法复现，排障成本极高。

### P1-3 models 整数组替换是读-改-写，与用户并发编辑存在丢配置竞态

- **位置**：`src/effort-core.ts:222-227`（整数组 set op）、`src/index.ts:164-225`（`runProvision` 先 `describe()` 取快照、后 `mutate`，两者之间无一致性校验）
- **问题描述**：dsh-settings 的 path 补丁穿不过数组中间节点，所以对显式 `models` 数组只能整体替换。快照读取与写入之间没有 revision 校验：若用户此刻正在 DSH 设置页编辑该 provider（新增模型、改字段），插件用旧快照生成的整数组会覆盖掉用户尚未反映在快照里的修改。更糟的是写入后的 `document-updated` 回声会触发复判，此时快照已经是被覆盖后的状态，幂等检查认为「无需再写」，用户的修改就永久丢了。
- **优化建议**：短期：`mutate` 前重读一次 `describe()` 并与计算 ops 用的快照比对，不一致则放弃本轮（下一个事件会再来）；长期：跟踪 `document-updated` 携带的 revision，若写入前发现 revision 已前移则重走一遍。若 SettingsForms 本身提供 CAS 语义则直接采用。
- **实施难度**：中。需要在宿主半区引入快照版本概念，并为「放弃-重试」路径补集成测试。
- **为什么这么定级**：这是唯一可能造成用户数据丢失的问题，所以不能放 P2；但触发窗口很小（要求用户编辑设置与某个供给触发事件在同一瞬间撞上），日常单用户场景概率低，够不上 P0。
- **一句话版本**：插件在你编辑模型配置的同时用一份旧快照整组覆盖回去，你刚加的模型可能被无声抹掉。
- **一个需要知道的取舍**：防御性重读每次多一趟 `describe()` 往返，而且「不一致就放弃」意味着高编辑频率下供给可能连续让路、迟迟不落地——需要配合有限次重试而不是无限重读。
- **事故是怎么发生的**：用户在设置页粘贴一个大 provider 配置还没保存完，恰好此时 `llm/adapters-updated` 触发供给 → 整数组写入旧快照 → 保存时冲突或新条目消失 → 用户配置丢失，且因为过程无任何报错，用户只会觉得「设置页莫名其妙丢东西」。

### P1-4 供给失效路径全部静默：重试 30 秒耗尽无日志、listModels 失败静默跳过、resolveModelInfo 异常被当成「无原生 reasoning」

- **位置**：`src/index.ts:129-145`（`RETRY_MAX = 60`，耗尽后无任何日志）、`src/index.ts:188-195`（`listModels` 的空 catch）、`src/index.ts:149-162`（`resolveModelInfo` 抛错时 `result = false` 并被 memo 永久记住）
- **问题描述**：三条独立的静默失败路径：① pi-ai 条目在 30 秒后才挂载（慢机器冷启动）→ 重试停止，供给永不落地；② 纯目录路由的 `listModels` 抛错（网络问题）→ `catalogIds` 置空 → 该路由本轮被跳过且无日志；③ `resolveModelInfo` 异常会被记成「无原生 reasoning」，此后原生模型也可能被写入 modelOverrides。
- **优化建议**：每条路径加一行 `logger.warn`（重试耗尽时说明「pi-ai 条目 30s 未挂载，供给已停止」）；`listModels` 失败时 warn 一次路由名；`resolveModelInfo` 异常与「确认无 reasoning」分开缓存（异常不 memo 或短 TTL）。
- **实施难度**：低。纯日志与缓存策略调整，不动写入逻辑。
- **为什么这么定级**：三条路径的最终表现一致——「自定义模型没有 Effort 行」，而这正是本插件存在的理由；用户端完全无法区分「插件坏了」「配置错了」「环境慢了」。之所以不是 P0，是因为多数情况下重启或等下一个事件能自愈。
- **一句话版本**：供给失败时用户看到的不是报错，而是插件最核心的功能凭空消失，且宿主日志里一个字都不会多。
- **一个需要知道的取舍**：日志加多会在 DSH 启动日志里产生噪音，对「没出问题」的用户是干扰；折中是失败路径必记、成功路径只保留现有的一行计数日志。
- **事故是怎么发生的**：低配机器冷启动要 40 秒，pi-ai 第 35 秒才挂载，重试第 30 秒已停 → 用户发现自定义模型没有档位可选 → 重启有时又好了（那次 30 秒内挂完了）→ 典型的「偶发、无法复现、查无此 bug」。

### P2-1 全文档 MutationObserver 常开，任何 DOM 变化都触发全量扫描

- **位置**：`src/client/index.ts:186-191`（`observe(document.body, { subtree: true, characterData: true })`）、`client/index.ts:118-128`（rAF 节流）
- **问题描述**：观察范围是整个文档且含 characterData——聊天流式输出时文本节点每帧更新，都会排队一次 rAF 全量扫描（`querySelectorAll('button[role="menuitem"]')` + 触发按钮扫描）。菜单未打开时扫描结果为空、单次成本很低，但这是与内容无关的持续开销，且与页面动画争抢 rAF 预算。
- **优化建议**：渐进降频——连续 N 次扫描零命中后把节流从 rAF 切到 150–250ms 间隔，一旦命中 Effort 行恢复 rAF；或在 observer 回调里做廉价预过滤（仅当 mutation 记录涉及 menuitem/aria-haspopup 相关节点才排队）。
- **实施难度**：中。降频逻辑本身简单，但要保证「菜单原子重挂载的第一帧就能涂色」不回退（现有 smoke 测试里 80ms 内完成的断言需要重新校准）。
- **为什么这么定级**：实际影响是「小而持续」而非「可感知卡顿」——菜单关闭时每次扫描接近免费。定 P2 是诚实的：它不是当前的性能瓶颈，但它是唯一随使用时长线性累积的 CPU 开销，修复收益稳定。
- **一句话版本**：只要页面有任何 DOM 在动（包括别人在打字、消息在流式输出），插件就在每帧做一次全文档巡逻。
- **一个需要知道的取舍**：降频后菜单行变色可能延迟几百毫秒才出现——功能不变，但「即时反馈」的打磨感会打折；这正是当初选 rAF 全扫描的原因，回调成本换响应感。
- **事故是怎么发生的**：用户开着长对话，流式输出持续数分钟 → DevTools Performance 面板里看到持续的脚本时间 → profile 定位到这个插件的 observer → 「插件让 DSH 变卡」的 issue（即使绝对开销可能只有百分之几）。

### P2-2 面板定位不跟随滚动/窗口变化，也没有 Esc 关闭和再次点击收起

- **位置**：`src/client/index.ts:158-167`（`showPanel` 一次性定位）、`client/index.ts:193-212`（无 keydown 处理；点击 Effort 行重新 render 而非 toggle）
- **问题描述**：面板按打开瞬间的锚点矩形做 fixed 定位，之后页面滚动或窗口 resize 面板悬在原地；没有 Esc 关闭；面板开着时再点一次 Effort 行不会收起（重新渲染同位置）。
- **优化建议**：加 `window` 的 `scroll`/`resize`（capture）监听：锚点元素仍在可视区就重算位置，锚点已卸载（`getBoundingClientRect()` 全 0）就直接关面板；`keydown` Escape 关面板；再次点击 Effort 行改为 toggle。
- **实施难度**：低。约 30 行监听与回收代码，全部纳入现有 disposer 即可。
- **为什么这么定级**：触发前提是「面板开着时去滚动」，属于低频操作序列；但一旦触发，视觉上就是明晃晃的 bug（浮层悬空），且三个小缺口（滚动/Esc/ toggle）是一类修复。
- **一句话版本**：面板打开后页面一动它就漂了，用户只能满屏幕找那个小小的 × 。
- **一个需要知道的取舍**：跟随滚动要处理锚点已 unmount 的情况（官方菜单关闭即卸载），此时「重算」没有意义，直接关闭是唯一正确行为——所以这个修复天然要求实现「锚点失效检测」，不能只加个 scroll 监听完事。
- **事故是怎么发生的**：用户打开面板 → 滚轮上翻想看看当前对话用的什么模型 → 面板脱离菜单悬在屏幕中部 → 用户下意识再点菜单行想「归位」，面板却纹丝不动 → 体验报告「浮层是个死的」。

### P2-3 面板用过的旧档位色会覆盖官方入口改档后的新文本

- **位置**：`src/client/index.ts:78`（`paintAllEffortRows` 无条件优先 `uiState.lastEffortId`）、`client/index.ts:95-115`（触发按钮同理）
- **问题描述**：着色优先级是「面板上报的 lastEffortId > 行内文本反推」。面板用过一次后，用户改走官方入口（如 /model 弹层）换档：菜单行文本由官方更新为新档位，但 observer 重涂时仍按旧的 lastEffortId 上色——行上写着「Low」却亮着 High 的紫色，直到下次打开面板才纠正。
- **优化建议**：涂色前先校验行内文本是否与 lastEffortId 的显示名一致；不一致回退到文本反推（`effortColorFromLabel`），都失败再退回 lastEffortId 或官方原色。
- **实施难度**：低。一个字符串比对 + 测试用例（smoke 里补「官方改档后面板未开」场景）。
- **为什么这么定级**：纯视觉不一致，不影响实际生效的档位（写入是正确的），所以进不了 P1；但「颜色」正是本插件的核心视觉语言，颜色说谎直接打击用户对插件的信任。
- **一句话版本**：菜单行文字已经换成 Low，颜色还停在刚才拖的 High 的紫色——两个信号打架。
- **一个需要知道的取舍**：自定义字典的档位名可能不在 `LABEL_ALIASES` 表里，此时文本反推会失败——策略必须是「宁可回退官方原色，也不沿用可能过期的颜色」；这意味着极少数自定义命名场景会失去着色，属于正确性优先的取舍。
- **事故是怎么发生的**：用户拖到 High（紫）→ 从官方 /model 弹层改成 Low → 关掉后菜单行写着 Low 亮着紫 → 用户截图问「到底哪个生效了」，顺手对插件的可靠性打了问号。

### P2-4 UI 文案硬编码中文，英文及其他语言用户看到中文提示

- **位置**：`src/client/effort/EffortPanel.tsx:199`（`aria-label="关闭"`）、`EffortPanel.tsx:246`（「模型目录加载中…」「当前模型不支持思考强度调节」）
- **问题描述**：面板内部所有用户可见文案都是中文字符串常量；菜单行识别倒是对英文做了兼容，但面板自己的提示没有。
- **优化建议**：最小双语文案表（仿照 `EFFORT_LABEL_TEXTS` 的探测方式，或读 DSH 的界面语言），把三处字符串收敛为一个 `t(key)` 函数；与 P0-1 的状态分支改造一并做最划算。
- **实施难度**：低。纯字符串重构，半天内完成。
- **为什么这么定级**：不影响功能、只影响非中文用户的理解成本，所以是 P2 而非 P1；但项目自己维护着七语 README，说明在意国际用户，文案是国际用户唯一 100% 会撞上的部分。
- **一句话版本**：README 翻译成了七种语言，面板报错只有中文。
- **一个需要知道的取舍**：引入完整 i18n 框架（语言包文件、复数、占位符）对插件体量是过度设计；双语文案表的代价是未来每加一种语言都要手动扩表，表会慢慢变大。
- **事故是怎么发生的**：英文用户遇到目录加载失败 → 弹出「当前模型不支持思考强度调节」→ 一个字看不懂 → 截图提 issue，标题是 "Chinese error message"。

### P2-5 刻度点/标签与滑块实际吸附位置系统性错位（首尾档约 10px）

- **位置**：`src/client/effort/EffortPanel.tsx:209`（标签 `10%..90%` 布点）、`EffortPanel.tsx:223`（刻度点同式）；对照 `effort.module.css:27`（thumb 宽 28px）
- **问题描述**：原生 range 的 thumb 行程是「半 thumb 宽 → 宽度-半 thumb 宽」（两端各缩进 14px），而刻度点/标签按容器宽度的 10%..90% 布点。五档时两端各偏差约 10px：第一档 thumb 中心在 ~14px 处，刻度点在 ~25px 处，方向相反的偏差出现在 MAX 端。
- **优化建议**：刻度点层左右留出 14px 内边距，布点公式改为 `calc(14px + (idx/(n-1)) * (100% - 28px))`，与 thumb 行程精确对齐；把 28px 提取为与 CSS 同源的常量（顺带解决 P3-4 里的 PANEL_W 双份问题）。
- **实施难度**：低。一个 CSS 计算式改动 + 视觉验收。
- **为什么这么定级**：不产生任何功能错误（吸附逻辑本身是对的），是纯视觉精度问题；但滑杆是产品的核心交互件，刻度与手感不对齐是用户一眼能看到的「不精致」。
- **一句话版本**：眼睛对准第一个刻度点，手指松开的位置其实差了半个 thumb。
- **一个需要知道的取舍**：对齐公式把 thumb 尺寸硬编码进了 JS/CSS 两处，将来调 thumb 大小必须同步改公式，否则错位从 10px 变成别的数字——把尺寸收敛为单一常量是这个修复的前置条件。
- **事故是怎么发生的**：有用户反馈「刻度和滑块对不上」→ 修复者只调了百分比没算 thumb 宽 → 某个档位对齐了、另一端更歪了 → 反复横跳两三轮才收敛。

### P2-6 滑杆对屏幕阅读器不可命名（无 aria 标注）

- **位置**：`src/client/effort/EffortPanel.tsx:229-242`
- **问题描述**：`input[type=range]` 没有 `aria-label` 与 `aria-valuetext`，读屏用户只会听到「28、35…」这样的裸数字，不知道滑杆是什么、当前档位叫什么。键盘可达性本身是好的（range 原生方向键 + blur 提交）。
- **优化建议**：加 `aria-label="思考强度"`（随 P2-4 的文案表走），拖动/同步时更新 `aria-valuetext` 为当前档位显示名（如「High」）。
- **实施难度**：低。两个属性 + 一处同步逻辑。
- **为什么这么定级**：受影响用户面小，但 WCAG 4.1.2（名称/角色/值）是主流规范的硬性条款，且修复成本几乎为零——性价比极高的一项。
- **一句话版本**：读屏用户能拖动滑杆，但从头到尾不知道自己在拖什么。
- **一个需要知道的取舍**：`aria-valuetext` 需要在拖动的每一帧同步更新，更新太频繁时部分读屏器会刷屏；按档位变化（而非数值变化）更新是正确的折中。
- **事故是怎么发生的**：读屏用户拖动时只听到数字变化，无法确认档位 → 只能放弃使用面板、回退官方档位列表 → 插件对该用户等于不存在，且没人会为此提 issue。

### P2-7 没有 CI：lib/ 产物靠人肉同步，测试只在本地跑

- **位置**：仓库根目录（无 `.github/`）；`lib/` 提交进仓库是 GitHub 安装路径的依赖（README 明示）
- **问题描述**：四层测试质量很高但没有 CI 强制执行；`lib/` 是构建产物且被 `github:` 安装路径直接消费，「改了 src 忘了 build 就 push」会直接把旧产物发给用户。
- **优化建议**：GitHub Actions 一个 workflow：`pnpm typecheck` + `pnpm test` + `pnpm build` + `git diff --exit-code lib/`（产物不新鲜即失败）。矩阵只需要一个 Node 版本（单仓库小项目，别过度矩阵化）。
- **实施难度**：低。约 30 行 yaml。
- **为什么这么定级**：当前没有发生过产物漂移事故（git 历史干净），所以是 P2 防御项而非 P1；但项目的分发方式（提交产物）使这个风险天然存在且一旦发生影响所有 github: 用户。
- **一句话版本**：测试写得再好，没人逼着跑就等于可能没跑；产物是手搓的，就可能忘搓。
- **一个需要知道的取舍**：CI 里跑 build 要求锁定 pnpm/Node 版本，环境漂移会造成 CI 假红；lockfile 已经有了，这是一次性成本。
- **事故是怎么发生的**：修了一个 client bug → 测试通过 → 忘记 `pnpm build` → push → github: 安装的用户拿到的还是旧 client.js，issue 里「修了怎么没效果」，排查半天发现是产物没更新。

### P3-1（新增功能提案）供给诊断报告：让用户能看到「插件到底写了什么」

- **提案**：在 DSH 设置页的插件条目配置里加 `debugReport: boolean`；开启后每次供给在宿主日志输出逐条明细（route / model / 方言 / 写了 reasoningEfforts 还是 compat / 跳过原因），替代现在只有的一行计数 `provisioning N field(s)`。更进一步可在面板「不支持」提示旁注明「若为自定义模型请检查 enabled 与方言配置」。
- **实施难度**：中（日志明细半天；引导文案需与 P0-1 联动）。
- **为什么这么定级**：它是 P1-4 的功能化延伸——P1-4 让失败「有日志」，这项让成功「可核查」。不是缺陷修复而是排障能力建设，所以放 P3。
- **一句话版本**：用户现在只能看到「插件说它工作」，看不到「它实际干了什么」。
- **一个需要知道的取舍**：明细日志的行数与模型数量成正比，大目录用户开一次 debugReport 就是几十行日志；用开关默认关闭来平衡，代价是出问题时用户要先回去开开关再复现一次。
- **事故是怎么发生的**：用户配了 `defaultDialect: qwen` 但实际端点是 effort 方言 → 档位拖了没效果 → 用户不知道去哪验证方言配置 → 连续试错八种方言（现状只能这样），最后放弃并卸载插件。

### P3-2（新增功能提案）方言配置错误时的用户引导

- **提案**：无法从线级效果自动验证方言是否正确（插件看不到请求体），但可以做启发式：档位写入成功后 N 分钟内无任何会话使用新档位的记录（若宿主可观测）或至少在面板 tooltip 里解释「拖动无效？检查 routes.<路由> 的方言配置，见 README 方言表」。诚实地说：完全自动探测做不到，这一项的定位是「降低试错成本」。
- **实施难度**：高（有价值的部分依赖宿主可观测能力，纯文案部分价值有限）。
- **为什么这么定级**：用户痛点真实存在（方言配错 = 静默无效），但插件视角没有可靠的探测信号，强行做会产出误导性提示——一个「高级但半吊子」的功能不如不做，放 P3 等宿主能力。
- **一句话版本**：方言配错的表现和「模型不支持」一模一样，用户只能盲猜八个方言。
- **一个需要知道的取舍**：基于启发式的「你的方言可能配错了」提示一旦误报，用户会把正确的配置改错——这类提示必须给出「如何自行确认」的路径而不是直接下结论。
- **事故是怎么发生的**：README 方言表有八行，用户逐个试 → 每次试错都要改配置 → 重挂插件 → 重启 DSH → 半小时后放弃，社区里留下一条「对 XX 商家的模型不管用」的差评（实际是方言没配对）。

- **位置**：`src/client/index.ts:193-212`（捕获阶段无条件 `preventDefault` + `stopPropagation`）
- **提案**：拦截前检查目标行是否已被其他插件标记处理（如对方面板已打开），是则放行；自己处理后也留下可识别标记（`data-effort-panel` 已有，可再加行级标记）。README 目前只给了「手动关掉对方拦截」的人工建议。
- **实施难度**：中（需要与 aurora 皮肤的实际行为对表，无法单方面闭环）。
- **为什么这么定级**：冲突场景小众（需同时装两个同类插件），且已有 workaround 写进 README；运行时仲裁又依赖对方配合，单方面能做的有限。

- **事故是怎么发生的**：用户同时装了 dsh-ui-web aurora 皮肤与本插件 → 点击 Effort 行弹出两个面板叠在一起 → 用户以为 DSH 坏了，在两个项目下各提一个 issue。

## 3. 值得保留的亮点（评估中确认的优点，改动时不要破坏）

1. **纯逻辑抽离**：`effort-core.ts` 零依赖、纯函数，方言扩展是干净查表（`wireFor`），这是可维护性的根基。
2. **四层测试金字塔**（单测 → mock apply → 真实 cordis 接缝 → jsdom 冒烟），特别是 host-integration 里逐条复刻 pi-ai 校验规则的做法，把「写入会被宿主拒绝」这类问题挡在了发布前。
3. **幂等供给设计**：`isOurInjection` 区分「自己写的」与「用户声明的」，用户显式声明（`false` 或自定义字典）永远不被覆盖——这是对用户数据主权的正确态度。
4. **拖动防抢滑块**：`writtenEffortRef`/`syncedEffortRef` 双标记解决「目录回声把滑块从指针下抢走」，注释里连 bundler 对 `let x = null` 的误折叠都防了（`uiState` 用对象属性）。
5. **WebGL 优雅降级与生命周期**：无 WebGL2 仅 warn、context lost/restored 恢复、idle 帧计数、resize 防抖、disposer 全量回收。
6. **安全边界干净**：不读凭据、无自有网络、React 转义渲染、宿主写入字段白名单化（reasoningEfforts/compat）。
